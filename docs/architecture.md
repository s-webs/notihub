# Архитектура NotiHub

Актуально для рабочего дерева на 01.11.2026. Источник истины для модели данных — `prisma/schema.prisma`, для HTTP-контрактов — контроллеры в `src/` и публичная схема `/docs`.

## Назначение и состав

NotiHub принимает события от внешних систем и отправляет Telegram-сообщения по настроенным маршрутам. Backend: Node.js 22, NestJS 11, Prisma 7, PostgreSQL 16, Redis 7 и BullMQ 6. Админка: React 19, Vite 8, Tailwind CSS 4. Система не содержит клиентского SDK и шаблонов сообщений.

```mermaid
flowchart LR
  Source[Система-источник] --> Events[POST /events]
  GlitchTip[GlitchTip] --> Adapter[POST /webhooks/glitchtip]
  Events --> Service[EventsService]
  Adapter --> Service
  Service --> DB[(PostgreSQL)]
  Service --> Queue[(Redis / BullMQ)]
  Queue --> Worker[TelegramProcessor]
  Worker --> Telegram[Telegram Bot API]
  Worker --> DB
  Admin[React-админка] --> AdminAPI[/api/admin/*]
  AdminAPI --> DB
```

| Компонент | Код | Ответственность |
| --- | --- | --- |
| Приём событий | `src/events/` | Валидация, проверка токена, выбор проекта и типа, создание логов и заданий |
| Webhook-адаптер | `src/webhooks/` | Проверка отдельного секрета и преобразование GlitchTip в событие `app_error` |
| Очередь | `src/queue/` | BullMQ, лимит отправок на бот, повторы, восстановление зависших доставок |
| Telegram | `src/telegram/` | `sendMessage` с HTML и классификация ошибок |
| Администрирование | `src/admin/`, `admin/src/` | CRUD проектов, типов, ботов, маршрутов и журнал доставок |
| Наблюдение | `src/health/`, `src/monitor/`, `scripts/watchdog.sh` | Проверки зависимостей и прямые оповещения о сбоях |

## Модель данных

`Client` в коде — проект в интерфейсе. Его глобально уникальный `slug` передаётся как `client` в событии. `NotificationType` принадлежит одному проекту; код уникален в паре `(clientId, code)`. Одинаковый код допустим у разных проектов. `Bot` может использоваться в разных проектах.

| Сущность | Смысл | Важные связи и ограничения |
| --- | --- | --- |
| `Client` | Проект, slug, имя, активность | Уникальный slug; владеет типами и ключами идемпотентности |
| `NotificationType` | Код и имя события | Принадлежит проекту; уникален `(clientId, code)` |
| `Bot` | Telegram-токен и активность | Токен уникален; в ответах админского API замаскирован |
| `RoutingRule` | Куда отправлять конкретный тип | Ссылается на проект, его тип и бота; `chatId` — строка, `threadId=0` — без топика |
| `NotificationLog` | Одна попытка доставки по маршруту | Статусы `PENDING`, `SENT`, `FAILED`; хранит запрос и подготовленный текст |
| `EventIdempotency` | Ответ на уже принятое событие | Уникальная пара `(clientId, key)` |

Внешний ключ маршрута по `(client_id, notification_type_id)` не допускает тип другого проекта. Удаление маршрута каскадно удаляет его логи. Удалить проект, тип или бота, используемые маршрутом, нельзя. При удалении проекта без маршрутов его типы удаляются вместе с ним.

Миграция `20261101000000_project_notification_types` скопировала прежние общие типы в каждый существовавший проект и перенаправила маршруты на соответствующие копии. Новые типы создаются только внутри проекта.

## Обработка события

1. `POST /events` проверяет JSON и `EVENTS_API_TOKEN`, если он настроен.
2. `EventsService` ищет активный проект по `client` и тип по паре `(clientId, type)`.
3. Если `idempotency_key` уже сохранён для этого проекта, возвращается прежний ответ с `idempotent: true`.
4. Выбираются активные маршруты данного проекта и типа с активным ботом.
5. Для каждого маршрута создаётся `NotificationLog(PENDING)` и задание BullMQ с `jobId=logId`.
6. Воркер применяет лимит для бота, вызывает Telegram `sendMessage` и записывает `SENT` или `FAILED`.

Ответ HTTP 200 означает завершение приёма и постановки заданий, а не подтверждение доставки Telegram. При отсутствии маршрутов ответ содержит `matched: 0`, пустой `deliveries` и всё ещё `queued: true`; ориентируйтесь на `matched`.

Очередь настроена на 8 попыток с экспоненциальной задержкой от 2 секунд, конкуренцию 3 и общий лимит 20 заданий/с. Дополнительно Redis-счётчик ограничивает отправки на один бот (`TELEGRAM_RATE_LIMIT_PER_SEC`, по умолчанию 20/с). Повторяемые ошибки Telegram и сети отправляются повторно; окончательные ошибки переводят лог в `FAILED`. Сервис каждые 30 секунд проверяет до 50 логов `PENDING` старше минуты и восстанавливает отсутствующие или завершившиеся задания.

Гарантия доставки практическая **at least once**: при сбое после успешного ответа Telegram, но до записи `SENT`, сообщение может уйти повторно. Ключ идемпотентности защищает последовательные повторы входного события, но одновременные запросы с одним ключом могут создать дубли: запись `EventIdempotency` выполняется после постановки заданий.

## Текст сообщения

Сервис выбирает `payload.message ?? payload.text`. Если результат — непустая строка, он передаётся в Telegram как HTML без дополнительного экранирования. Иначе строится текст из полей `payload` с HTML-экранированием. Источник должен экранировать пользовательские вставки в готовом HTML-сообщении; неправильная разметка может привести к `FAILED`. Для сообщений в топик при `threadId > 0` передаётся `message_thread_id`.

## Доступ и интерфейс

- `POST /events` принимает Bearer или `X-Notihub-Token`, когда задан `EVENTS_API_TOKEN`; без переменной токен не проверяется.
- GlitchTip использует отдельный обязательный `GLITCHTIP_WEBHOOK_SECRET`.
- `/api/admin/*` использует Basic Auth (`ADMIN_USER`, `ADMIN_PASSWORD`). Админка хранит закодированную пару в `sessionStorage` текущей вкладки.
- Админка раздаётся под `/admin/` и использует hash-маршруты. Типы доступны через карточку проекта; старый UI-путь `/types` переводит к списку проектов.
- `/queues` и `/docs` не защищены админским Basic Auth; доступ к ним ограничивают на уровне сети или reverse proxy.

## Эксплуатация и ссылки

`GET /health` проверяет процесс, `GET /health/ready` — PostgreSQL и Redis (503 при недоступности). Docker entrypoint по умолчанию выполняет `prisma migrate deploy`. PostgreSQL хранит маршруты, токены ботов, логи и идемпотентность; Redis — очередь и лимиты. Для внешнего мониторинга предусмотрен `scripts/watchdog.sh`, который пишет в Telegram напрямую.
